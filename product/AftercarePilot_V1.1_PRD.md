# AftercarePilot V1.1 产品需求文档（PRD）

**版本**：v0.1（供原型设计、开发评审）\
**日期**：2026-11-12\
**负责人**：项目作者（独立个人项目）\
**项目类型**：ToB AI 辅助售后处理 / Agent 人机协同\
**产品目标**：将 V1.0 的“功能正确”提升为“客服能看懂依据、知道下一步、不会误解操作结果”。

> **证据与状态说明**：本 PRD 依据 `00-v1-baseline.md`（Git 基线 `1b0276b`）、三张 V1.0 运行截图与 `03-AftercarePilot-V1.0-产品体验评审-v0.1.md` 编写。作者已完成开发者自测；截至本版**没有外部真实客服的用户研究记录或量化体验改善结果**。本文的 V1.1 功能是**待实现需求**，验收标准是预定条件，并非已通过的测试。

## 1. 背景、问题与目标

### 1.1 产品定位

面向**电商一线售后客服专员**的 AI 辅助受理工作台。客服录入客户问题；系统查询订单、退货政策和资格事实；AI 生成处理建议与尚未发送的回复草稿；客服人工审核，必要时确认创建**内部售后工单**；后端执行版本、规则和重复提交校验并回读结果。

**责任边界**：AI 负责理解、建议和拟稿；确定性规则负责退货资格和金额；客服决定是否确认；FastAPI 服务端执行审批与建单。创建内部工单 **≠** 向客户发送消息 **≠** 自动退款 **≠** 退货完成。

### 1.2 V1.0 已有能力（不作为 V1.1 新功能）

- Streamlit 双主导航：售后请求 / 售后工单；请求筛选、归档、历史版本、操作记录。
- 订单查找与补录、意图识别、MCP 只读查询、退货资格规则、结构化 Proposal 和证据折叠区。
- 草稿编辑与保存、确认草稿、暂不采用、确认并创建工单；事务、防重复、版本/hash 校验、独立结果回读和待核验。
- 已有合成场景和工程回归；这些**不能代替**真实客服的可用性或效率评估。

### 1.3 从截图确认的可用性风险（启发式判断）

1. 两种不同业务结果在顶部均显示“待确认”，需要操作者自己进一步推断确认对象。
2. 主要判断结论很醒目，但关键业务事实与政策原文需要额外查找；不能假定已被实际查看。
3. “申请已受理”与退款完成、客户消息发送容易被混同，需在实际操作区明确区别。
4. 缺订单号时，首屏缺失信息提示与补录入口的关联不明显。
5. 未符合资格的场景仍突出“申请金额”，退货窗口未开始却显示“截止：未知”，存在语义风险。
6. “请补充：订单号。没有创建工单”放入回复草稿，混杂内部状态与对客可发送文案。

以上是设计假设；并不声称已被真实用户实验证实。

### 1.4 V1.1 版本目标

- **可理解**：客服在当前页面能快速辨认资格结论、关键依据和确认对象。
- **可操作**：缺信息、可建单、仅确认草稿、待核验等不同状态分别提供明确下一步。
- **可控**：所有确认操作保留原有后端重新核验、防重复、事务及审计机制。
- **可追溯**：页面呈现的依据能回到已有订单/政策/资格证据，不凭 LLM 生成未经核实的理由。

### 1.5 非目标（Out of scope）

自动退款、退换货履约、物流面单、主动给客户发送消息、工单多级流转、真实商家系统接入、团队分配/多租户权限、生产 SLA、替换 LangGraph 为 Dify。

## 2. 用户、场景、核心任务

**主用户**：一线售后客服；单人操作台，当前没有成熟的多角色 RBAC。\
**用户故事**：作为售后客服，我希望在处理客户退货诉求时，直接看到订单与政策依据、当前需要的操作和该操作的真实后果，以避免误操作或给出错误承诺。

| 任务 ID | 情境 | 用户期望 | 系统必须做的事 |
| --- | --- | --- | --- |
| T-01 | 已签收，规则判断可退货 | 核对理由并创建内部工单 | 展示依据、可编辑草稿、二次确认和结果回读 |
| T-02 | 未签收/规则判断暂不满足退货 | 给出合规解释，不误建单 | 标示仅需确认回复；不出现可执行建单入口 |
| T-03 | 用户未给订单号 | 明确知道缺什么，并尽快补齐 | 订单号缺失提示+查找/输入入口，补齐后重分析 |
| T-04 | 建单请求响应丢失 | 确认是否已成功，避免重复点击 | 待核验状态+独立查询按钮；禁止再次直接提交 |
| T-05 | 证据未知/冲突/规则异常 | 不凭空答复或执行 | 显示“需人工核实”/失败及下一步提示 |

## 4. 信息架构与页面结构

### 4.1 详情页从上到下的建议顺序

1. **请求头**：请求编号 / 当前真实业务状态 / 订单号（已知时）/ 返回列表。
2. **下一步行动卡**：一句话回答“现在该做什么？”，不使用无对象的“待确认”。
3. **决策概览**：规则判定的资格、相关事实、政策依据、缺失项（应显示来源标签，严禁以 LLM 文字代替规则事实）。
4. **客户回复草稿**：明确“尚未发送”，可编辑或复制，保存修改后才允许确认。
5. **审批与确认操作**：只展示当前状态允许的动作，附近明确写出实际后果。
6. **完整证据与历史记录**：保持现有折叠式详细信息，供深入核查。

建议保留当前“售后请求/售后工单”主导航，不为 V1.1 设计新的复杂系统。

### 4.2 页面三态

- **A 可建单**：`待确认` + `eligible` + `return` 方案 → 页面解释为“待确认建单”。常显资格原因、订单签收、政策期限与金额；主动作“确认并创建内部工单”；显示“不会直接退款/发送回复”。
- **B 仅确认草稿**：`待确认` + 当前没有可执行建单资格/仅回复方案 → 页面解释为“待确认客服回复”；主动作“确认回复草稿（不建单）”；订单金额不得称已批准退款金额。
- **C 待补充**：`待补充` → 页面解释为“缺少订单号/具体字段”；主动作指向订单查找或补录输入框；不展示可用的建单操作。

**重要**：前端的“待确认建单”“待确认回复”是**派生的用户友好标签**，不新增同名后端业务状态。应以 Proposal 类型、资格事实和后端允许的 action 为唯一判定源。仅靠资格 `eligible` 不足以保证可建单，仍须服从当前方案类型与后端校验结果。

## 5. 详细功能要求和验收标准

### FR-01：状态与下一步行动面板（P0）

**触发**：进入请求详情页或请求状态更新后。\
**数据来源**：后端当前 Proposal、业务状态、允许的操作与资格事实。\
**展示规则**：
- `待补充`：指出具体缺失项，显示“补充订单信息/查找订单”。
- `待确认` 且允许建单：显示“请核对依据后创建内部售后工单”。
- `待确认` 且仅可确认草稿：显示“请核对并确认客户回复草稿”。
- `待核验`：显示“提交结果尚未确认”，仅提供“查询提交结果”。
- `需人工处理`、`分析失败`、`需重新分析`：按照既有失败原因显示核实/重试路径；不得伪装为可以直接建单。
- `申请已受理`：显示“内部售后工单已创建”，并提供关联工单入口，明确退款仍需后续流程。

**验收 AC-01**：同一后端“待确认”状态在“可建单”和“仅草稿”两种测试样例下呈现不同操作文案。\
**AC-02**：页面提供动作时，其可用性与后端允许动作一致；不增加前端绕过资格校验的路径。\
**AC-03**：待核验情况下不提供可再次触发建单的主按钮。

### FR-02：可核查的决策依据摘要（P0）

**触发**：存在有效的订单/政策/资格查询结果时。\
**显示字段**：订单号、订单实际状态（如未签收/已签收）、退货原因、资格结论及原因码解释、政策窗口及截止时间（如适用）、金额和币种；未知数据明确标注未知原因。\
**约束**：证据须来自结构化事实和规则结果；生成式文本仅作为解释，不能被当作唯一证据。详细原始证据保留展开入口。

**AC-04**：在 A/B 两种测试用例中，无需展开多层折叠即可见关键事实及资格结论。\
**AC-05**：数据缺失时不虚构签收/期限/退款数额，显示缺失或无法计算原因。\
**AC-06**：展开详细依据后能看到与摘要对应的现有订单/政策/资格记录。

### FR-03：确认动作与业务后果（P0）

**规则**：
- 可建单：主动作“确认并创建内部售后工单”；旁注“不直接退款、不自动发送客户回复”。必要的最终确认弹层复述订单、方案及后果。
- 仅确认草稿：主动作“确认回复草稿（不建单）”；明确“草稿尚未发送”。
- 草稿有未保存编辑：沿用 V1.0 禁止直接确认的校验，优先引导“保存修改”。
- 提交由现有 FastAPI 审批服务处理，仍校验版本、hash、订单状态、政策与资格，返回工单回读结果。

**AC-07**：确认建单弹层中明确本操作产生内部记录，不宣称退款或消息发送成功。\
**AC-08**：未保存草稿、过期方案、版本冲突和重复提交仍按现有后端策略拦截或回读。\
**AC-09**：操作成功后显示内部工单编号与“查看工单”入口；不使用“退款成功”文案。

### FR-04：缺失信息引导（P0）

**规则**：
- `待补充` 时在页首显示缺失字段（如订单号）与可执行下一步。
- 对缺订单号的情形，主操作定位或展开已有“查找订单”区域；也可允许人工补录后重新分析。
- 对多个候选订单，必须让用户选择具体订单；不能自动猜测。
- 补齐后沿原请求生成新版本并重新分析。

**AC-10**：在“我想退鼠标但没提供订单号”样例中，首屏可见“缺少订单号”及补录/查找动作。\
**AC-11**：未补齐必要事实前，不允许建单。\
**AC-12**：补录后继续关联原 `request_id`，历史记录不丢失。

### FR-05：对客草稿与内部说明分离（P0）

**规则**：
- 对客回复草稿仅包含可向客户传达的内容；需要客户补订单号时可说“请提供订单号”，但“没有创建工单”“当前未写入数据库”等内部状态应呈现在客服工作台提示区。
- “尚未发送”始终可见；复制草稿不意味着自动发送。
- 若原 Agent 输出中混有内部标记，优先从结构化字段/展示分层解决；若需改生成规则，保持现有模型回归与业务校验。

**AC-13**：待补充样例中，回复草稿不包含内部执行说明；内部信息在独立区域清晰可见。\
**AC-14**：复制/确认草稿不触发客户消息发送。

### FR-06：金额与期限语义（P1）

**规则**：若订单暂不符合条件，不以大号“申请金额”暗示已获退款资格；可展示“订单金额（仅供参考）”。签收窗口尚未起算时写“退货期限尚未开始”，与“数据缺失导致无法判断”区分。\
**AC-15**：未签收样例不会出现“已核准退款 89.99 美元”等误导性表述。\
**AC-16**：系统不凭空展示未计算出的截止日期。

## 6. 业务状态映射（前端展示规则草案）

| V1.0 实际状态 | V1.1 首屏业务说明 | 用户下一步 | 注意 |
| --- | --- | --- | --- |
| 分析中 | 正在分析客户问题 | 等待结果 | 保留进度反馈，不许多次提交 |
| 待补充 | 需要补充订单号/指定信息 | 查找或补录，重新分析 | 禁止建单 |
| 待确认 | 待确认建单 **或** 待确认回复 | 审阅与提交允许的动作 | 必须以方案类型/动作权限细分 |
| 申请已受理 | 内部售后工单已创建 | 查看关联工单 | 非退款完成 |
| 草稿已确认 | 客服回复草稿已确认 | 复制/交接后续沟通 | 非客户消息已发送 |
| 需人工处理 | 当前无法自动给出可靠结论 | 人工核实 | 不伪装为可自动执行 |
| 方案未采用 | 本次建议未被采用 | 查看原因/必要时重新分析 | 保留记录 |
| 需重新分析 | 方案已过期或事实变化 | 重新分析 | 不复用旧确认动作 |
| 分析失败 | 本次分析未成功 | 查看错误后重试 | 不凭空生成结论 |
| 待核验 | 提交结果需要核验 | 查询提交结果 | 禁止直接重复建单 |

**归档是独立属性，不是以上业务状态之一**；请求列表当前“处理中”表示未归档，后续可通过文案改为“未归档”。

## 7. 低保真原型设计规范

**原型范围**：仅对请求详情页制作三态 A（可建单）、B（仅回复）、C（待补充），以及可建单的二次确认弹窗。可复用相同页面布局，不必另画所有模块。\
**设计宽度**：1440px 桌面端。\
**必备区块**：请求头/当前行动/关键依据/草稿/操作后果/详细证据。\
**交互**：状态切换仅用于演示；正式实现须由真实业务状态和后端权限决定。\
**现状图**：使用 V1.0 的实际截图作为对照，不把改造后样稿宣称为已上线页面。

## 9. 风险与依赖

1. **不新增后端状态枚举**：展示标签由当前 Proposal、允许动作和资格事实派生，避免破坏兼容性。
2. **异步/待核验路径**：前端不能凭展示逻辑自动重试建单；复用独立结果回读。
3. **AI 幻觉**：政策依据与资格必须使用真实结构化数据；用户可见解释不能与规则事实矛盾。
4. **开源归属**：明确 AftercarePilot 基于上游项目二次开发；外发仓库与素材须符合上游许可证。
5. **用户研究证据不足**：当前可完成产品定义和原型，但不能宣传“客服效率提升”“真实客户满意度改善”。

## 10. 产品方案决策记录（ADR）

| 决策 | 理由 | 备选方案与取舍 |
| --- | --- | --- |
| 优先优化现有请求详情页 | V1.0 已有完整处理闭环；当前关键风险在信息理解与下一步操作 | 不新建复杂五页系统，控制工作量 |
| AI 建议与确定性资格分层展示 | 避免把生成式文本当成业务事实 | 不把所有政策依据藏在 LLM 自然语言中 |
| 确认对象明确区分 | 建单、确认草稿的后果不同 | 不通过笼统“确认”按钮承载不同业务操作 |
| 先 PRD + Figma，再 Codex 修改代码 | 产品方案先可视化、可核对、可验收 | 不在需求不清楚时直接重构架构 |
| Dify PoC 暂缓 | 本轮不为工具关键词引入无关重构 | 作为后续方案选型实验独立开展 |
