# AftercarePilot V1.1｜Product Brief（v0.1，待验证）

> 状态：产品假设草案，**不是**已完成用户调研或已上线功能。\
> 基线依据：用户提供的《AftercarePilot V1.0 只读审计报告》，本地 main 提交 `1b0276b`，上游对照 `3d38d5a`。\
> 待补证据：三组真实运行截图、目标用户访谈与任务测试。

## 1. 产品定位

**一句话**：面向电商一线售后客服的 AI 辅助受理与内部售后建单工作台，让客服在有依据、可修改、可核验的前提下处理退货申请。

**目标操作者（V1.1 主角色）**：售后客服专员，兼任当前系统中的人工建议审核人。当前系统是本地单人操作员工作台，**尚不支持以已验收的多角色分权或多人协作能力对外描述**。

**业务范围**：客户售后问题录入、必要信息补录、订单/退货政策/资格查询、AI 建议与回复草稿、人工决定、创建内部售后工单、查看/核验结果。

**非目标**：自动退款、退换货履约、物流面单、给顾客实际发送消息、企业多租户部署、客服团队任务分配和生产 SLA。内部“申请已受理”不等于退款或退货完成。

## 2. 已实现的 V1.0 能力（事实）

- 技术链路：Streamlit → FastAPI → LangGraph/规则 → 只读 MCP/业务数据 → 结构化 Proposal → 人工审核 → 后端校验与事务建单 → 结果独立回读。
- 具有请求与工单两个主导航；请求筛选、补录、历史版本、查看事实证据、编辑回复草稿、确认草稿、拒绝/暂不采用、确认并创建工单、待核验查询均已具备。
- 业务规则负责退货资格；AI 负责理解与建议；人工决定是否确认；后端负责提交时重新校验。仅有内部工单创建和核验，不含实际退款执行。
- 质量证据为历史工程/合成场景和模型回归；当前**没有**目标客服的真实可用性测试或处理效率数据。

## 3. V1.1 待验证的用户问题

| 编号 | 基线证据（事实） | 风险假设（尚未验证） | 验证方法 |
| --- | --- | --- | --- |
| H1 | 列表“处理中”实际指未归档，可能包含已受理记录 | 用户可能把它当“待办”队列 | 混合状态列表找待处理请求、解释筛选含义 |
| H2 | 订单选择在折叠区，待补充使用通用文本框 | 遇到缺订单/多候选订单时，不清楚下一步 | 缺单号、多候选订单的任务观察 |
| H3 | 资格、政策等依据可在详情折叠区查看 | 可能不看证据直接确认，或难以理解 AI 判断 | 完成审批前复述资格、政策和金额依据 |
| H4 | “确认草稿”“确认并创建工单”“申请已受理”各有不同语义 | 用户可能误以为已发客户消息或退款完成 | 点击前后让用户解释系统发生了什么 |
| H5 | 提交响应丢失时进入“待核验”，另有“查询提交结果” | 用户可能重复点击或无法辨别等待中的状态 | 在可控测试环境模拟待核验场景 |

## 4. 版本目标（待访谈校准）

- **业务正确性**：客服理解操作边界，在批准前能核对依据，不把内部工单当成退款完成。
- **任务可完成性**：在缺信息、审批、执行待核验等核心场景知道下一步要做什么。
- **产品可解释性**：区分规则计算的资格结论与模型生成的建议，并能查看可追溯证据。

## 5. 功能候选清单（不代表已经确认开发）

| 优先级（暂定） | 候选改动 | 设计边界 |
| --- | --- | --- |
| P0 | 请求列表标签与状态含义澄清 | 仅把“处理中”改叫“未归档”属于文案；真正的“待办队列”需要新增筛选逻辑，不能混为一谈 |
| P0 | 审批前的决策依据摘要区 | 展示已有事实/资格/政策数据，不凭空生成“依据” |
| P0 | 明确三类操作结果：草稿确认、内部工单受理、待核验 | 不承诺自动发送回复或退款成功 |
| P1 | 缺订单号、多候选订单时的定向补录引导 | 先验证错误路径，再定具体交互 |
| P1 | 待核验/失败状态的下一步指引 | 保留后端已有重复提交保护与独立回读机制 |
| 暂不做 | 真实退款、多角色权限、任务分配、外部消息发送 | 超出现有 V1.1 工作范围 |

## 6. 候选指标与测量方式

| 指标 | 测量方式 | 说明 |
| --- | --- | --- |
| 任务完成情况 | 每位参与者在同一模拟任务中是否独立完成 | 小样本探索性结果，不作为总体完成率宣传 |
| 决策语义理解 | 请用户复述点击“确认草稿”“确认并创建工单”的后果 | 记录误解和纠正次数 |
| 查找依据时间 | 从进入方案详情到找到订单/政策/资格依据的耗时 | 与任务难度一起记录 |
| 错误操作/求助次数 | 观察并记录 | 需区分界面问题、业务知识不足与测试材料问题 |
| 复测改善 | 针对同一问题验证新原型能否解决 | 记录学习效应和样本差异，避免夸大因果 |

## 7. 需要下一步核实的问题

1. 用户截图实际显示哪些字段、按钮及错误状态？哪些信息虽然由后端保存，却在界面上不可见？
2. “确认草稿”是否容易被误解为已发送客户？页面是否明确说明未发送？
3. 订单资格和政策依据实际需要几步才能查看？
4. 当前合成数据能否稳定演示缺订单号、多候选订单和待核验？若不能，先由 Codex 设计隔离测试夹具，不改业务生产逻辑。
5. 是否能联系至少 2–3 名有客服/售后经验的受访者，先访谈真实处理流程？
